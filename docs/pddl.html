Supported PDDL

PlanForge reads a grounded fragment of numeric PDDL. This page lists what the translator accepts, construct by construct, and then the limits. Some of those limits are reached by an explicit error naming the construct. Others are not: a few constructs are parsed and then quietly ignored, and those are listed first, because they are the ones that can cost you a correct answer.

Requirement levels

The accepted fragment is PDDL 2.1 level 1 — propositional and numeric, without time — plus PDDL 2.2 derived predicates. Stated as :requirements flags, so that it is checkable:

Each row was checked by running the translator on a task that uses the construct, except :duration-inequalities, :continuous-effects and :goal-utilities, for which no handling exists anywhere in the code and the row is established by reading it. "Ignored" means the construct parses and then has no effect, which is not the same as being rejected.
FlagStatusDetail
:stripsSupportedThe base language.
:typingSupportedIncluding type hierarchies. Types are compiled into predicates before grounding. (either a b) is not read and fails on the type token.
:negative-preconditionsSupported(not (p ?x)) in preconditions, goals and effect conditions. Only around a single atom or a comparison — (not (and …)) and (not (or …)) fail.
:action-costsSupported(increase (total-cost) …) at the top level of an effect. Costs must be non-negative integers; a non-integer cost is rejected.
:numeric-fluents / :fluentsSupportedThe main extension. See Effects and Conditions.
:derived-predicatesSupported(:derived …), layered and recursive, and exists works inside a derived body. Several :derived blocks for the same head act as a disjunction, which is the working way to write one — an or inside a single body is not. 18 fixtures cover this.
:equalityPartial(not (= ?x ?y)) works: every object is made equal to itself in the initial state, so inequality is statically decided. A positive (= ?x ?y) between objects is misread as a numeric comparison and removes the action.
:disjunctive-preconditionsPartialAn or in an action precondition is compiled away correctly, by splitting the action into one copy per disjunct. An or anywhere else is ignored — see below.
:conditional-effectsPartialwhen guarding a single propositional or numeric effect works. A conjunctive consequent, (when C (and A B)), fails.
:universal-preconditions, :existential-preconditions, :quantified-preconditionsIgnoredNot implemented. See the warning below.
:adlNot supportedADL requires quantified preconditions and universal effects. Both are ignored rather than implemented, so this fragment is not ADL whatever the flag says — and since the flag is not read, declaring it changes nothing.
:object-fluentsRejectedA typed function return is parsed and discarded, and an object-valued entry in :init is then an explicit error: numeric init fact for PNE loc-of(t1) must assign a numeric constant, got PNE p1().
:durative-actions, :duration-inequalities, :continuous-effects, :timed-initial-literalsNot supportedNothing temporal. A (:durative-action …) block is an unknown section: it is skipped with a warning, leaving the domain with no actions, and translation then fails on the first unreachable goal atom. A timed initial literal, (at 5 (p)) in :init, fails on its nested literal.
:preferences, :constraintsNot supportedNo PDDL 3. A (preference …) in a goal fails. A problem-level (:constraints …) is dropped with no message at all, so the plan silently ignores it.
:goal-utilitiesNot supportedNo soft goals and no utilities.

The declared requirement list is never checked

:requirements is parsed for its shape and dropped; nothing downstream consults it. So the flags above are a description of the implementation, not something the planner enforces, and declaring :adl or :durative-actions produces no complaint by itself. What is supported is decided construct by construct, where the construct is used.

Constructs that fail quietly

Four constructs are parsed and then ignored

These are bugs, not design decisions, and they are the reason this page leads with them. In each case the input is accepted, no warning is printed, and the task that gets grounded is not the task you wrote. Each row was confirmed by running the planner:

ConstructWhat happensConsequence
forall in a precondition, goal or axiom bodyTreated as true. The quantifier-removal pass rebuilds the quantifier instead of expanding it, and nothing downstream reads it.An invalid plan. An action whose forall precondition is false is applied anyway.
or outside an action precondition — in a goal, a :derived body or an effect conditionTreated as true. Only action preconditions are split into disjuncts, and a disjunctive goal is replaced by a goal-reachability axiom before that split would see it. For an axiom, write one :derived block per disjunct instead; that works.An invalid plan. A disjunctive goal is reported solved by the empty plan.
forall in an effectDropped. The effect's quantified parameters are never bound to objects, so the effect atom keeps its variable and matches nothing.A missed plan: the search reports no solution where one exists.
exists in an action preconditionRemoves the action. The bound variables are appended to the action's parameters without updating its external-parameter count, so no instance of it survives grounding. (Inside a :derived body, exists is fine.)A missed plan.

A fifth, narrower case: imply is correct when its antecedent is a single literal, which is the usual way it is written, but with a compound antecedent the antecedent is not negated — (imply (and (p) (q)) (r)) is compiled as (p) ∧ (q) ∨ (r) rather than ¬((p) ∧ (q)) ∨ (r).

Until these are fixed, the safe reading is the flag list above: the translator is a STRIPS-plus-numbers-plus-axioms translator, and quantifiers belong only inside :derived bodies.

Input

Two positional arguments are a domain and a problem. One positional argument is a pre-translated SAS+ file.

planforge --search 'astar(lmcutnumeric())' domain.pddl problem.pddl
planforge --search 'astar(lmcutnumeric())' task.sas

On the PDDL route, translation and grounding happen in process: no SAS+ text is produced on the way to the planner's own search. When you want the text itself — to hand the task to another planner, or to attach it to a bug report — use the second binary, which stops after translation:

planforge-translator translate domain.pddl problem.pddl --output task.sas

Without --output it writes output.sas. Its one other option is --layer-strategy, which chooses how derived variables are spread over axiom layers: min, the default, puts as many as possible into one layer, and max gives every variable a layer of its own unless it sits in a cycle. A value that is neither is rejected while the command line is parsed:

$ planforge-translator translate --layer-strategy nope domain.pddl problem.pddl
error: invalid value 'nope' for '--layer-strategy <LAYER_STRATEGY>': unknown layer strategy "nope"; use `min` or `max`

Both routes reach the same task. Translating the delivery fixture from the quick start and searching the resulting SAS+ file reports the same 49 propositional and 12 numeric variables, expands the same 73 states and returns the same cost-22 plan as the single-call pipeline.

Domain sections

SectionHandling
:requirementsAccepted and ignored; see Requirement levels. The planner does not gate on the declared flags, so what it supports is decided construct by construct — usually where the construct appears, but for the four cases under quiet failures, not at all.
:typesRead, including type hierarchies. Untyped parameters default to object.
:constantsRead.
:predicatesRead.
:functionsRead. These are the numeric fluents.
:actionRead: :parameters, :precondition, :effect.
:derivedRead. Derived predicates become axioms, arranged into layers.
:global-constraintRead, as an axiom. A constraint required to hold in every state.
:axiomRejected, deliberately. PDDL 2.1's (:axiom :vars ... :context ... :implies ...) is a different block shape, not another spelling of :derived, and parsing it as one would silently mistake :vars for the head predicate. The error tells you to write (:derived (NAME ?x - t) CONDITION) instead.
anything elseSkipped, with a warning naming the section.

Conditions and goals

In preconditions, goals, axiom bodies and effect conditions:

  • Atoms and negated atoms. not around a single atom or a comparison. not around a compound — (not (and …)), (not (or …)), (not (exists …)) — is not read and fails on the inner list.
  • and, everywhere.
  • or, in an action precondition only, where it is compiled away by splitting the action into one copy per disjunct. Elsewhere it is ignored.
  • exists, in a :derived body only, where the bound variables become axiom parameters. In an action precondition it removes the action.
  • Numeric comparisons <, <=, =, >=, >, each over exactly two operands, and each also usable negated inside not. A comparison becomes a condition variable of its own, which is what lets the numeric CEGAR loop refine its operands.
  • imply, with a single-literal antecedent. A compound antecedent is mis-negated.
  • forall is parsed and then treated as true. Do not use it.

= is read as a numeric comparison whenever it is not directly inside a not, so it works between fluent expressions, and (not (= ?x ?y)) works as object inequality — the initial state asserts (= o o) for every object, which is what makes that decidable. A bare positive (= ?x ?y) between two objects, however, is read as a comparison between two zero-ary fluents and removes the action.

Effects

  • Conjunctions of effects, and negated atoms as delete effects.
  • Conditional effects — when, guarding one propositional or numeric effect. The consequent must be a single effect: a conjunctive consequent, (when C (and A B)), is not read and fails on the inner list. Write one when per effect instead.
  • Numeric assignment — all five PDDL operators: assign, increase, decrease, scale-up, scale-down. The target must be a primitive numeric expression, that is a function applied to arguments, rather than a compound expression.
  • Universal effects — forall — are not supported. The block is parsed and then dropped, so the effect never happens and the search reports no solution rather than an error.

Numeric expressions

Inside comparisons and assignments: numeric constants, function applications, the binary and n-ary operators +, -, *, /, and unary - as additive inverse. The fluent total-cost is recognised as the integer cost accumulator.

Problem sections

  • :objects, :init — including numeric initial assignments — and :goal.
  • :metric with minimize or maximize. See the limit below.

What the translator emits

The output is Fast Downward's SAS+ text format, declared as version 4: the familiar layout, plus the sections the numeric extension needs. These are all of them, and every one appears in real output from the fixtures in this repository:

SectionCarries
versionThe format version, 4.
metricThe direction, and the numeric variable being optimised.
variableOne per finite-domain variable: its name, its axiom layer (-1 when no axiom derives it), its domain size and one name per value.
mutex_groupInvariant-derived mutex groups, when the invariant analysis finds any. The blocks-4-0 fixture yields five.
stateThe initial value of every finite-domain variable.
goalThe goal as variable/value pairs.
operatorOne per grounded action: name, prevail conditions, effects with their own preconditions and conditions, and the cost.
ruleOne per grounded propositional axiom, which is how :derived predicates arrive.
numeric_variablesThe numeric variables and their kind: regular, constant, cost or derived.
numeric_stateTheir initial values.
comparison_axiomsOne per numeric comparison, giving the comparison its own derived variable — the thing the numeric CEGAR loop refines.
numeric_axiomsAssignment axioms: the flattened arithmetic, one operator per node.
global_constraintThe constraint required to hold in every state.

So the delivery fixture from the quick start comes out as 49 finite-domain variables, 12 numeric variables, 136 operators and one axiom rule.

The reader parses the declared version but does not gate on it — a file declaring version 3 is read without complaint — so what actually has to match is the section layout, not the number.

Limits

Abstractions require a conjunctive goal

Abstract operators are derived from task operators, and no task operator writes a derived variable — only the axioms do. A goal on a :derived predicate is therefore a goal an abstraction has nothing to reach for. Rather than let each abstraction family invent its own reading of such a goal, all of them refuse the task and name the variable and its axiom layer:

Error: Custom { kind: Other, error: "failed to build domain abstraction: CEGAR failed to build abstraction: abstractions support conjunctive goals only: goal fact Fact(var: 4, value: 0) names the derived variable \"var4\" (\"\") in axiom layer 1, which no operator writes" }

This covers a :derived predicate placed in the goal, and the goal-reachability predicate the translator introduces for a disjunctive, quantified or nested goal. Numeric comparisons are deliberately unaffected: a comparison variable is derived in the SAS sense too, but refining a comparison's operands is exactly what the numeric CEGAR loop does.

Nothing else is restricted this way. The same fixture that the domain abstraction refuses above solves normally under astar(lmcutnumeric()), at cost 5, because non-abstraction heuristics test the goal in a state the axiom evaluator has already closed.

Other limits, plainly

  • Plan metrics must name a single fluent. (:metric minimize (total-cost)) is used as written. A compound metric expression is not supported: it is replaced by total-cost, without an error. If your task minimises an arithmetic combination of fluents, PlanForge is not optimising what you wrote.
  • Pattern databases and Cartesian abstractions need a restricted task. Pass --restrict-task, or supply a task that is already restricted. Asking for these heuristics without it is an error that names the offending comparison axiom rather than a silent conversion.
  • Comparisons are binary. A comparison with more or fewer than two operands is rejected.
  • Assignment targets are primitive. The left-hand side of an assignment effect must be a function application, not an expression.
  • Sequential plans only. There are no durative actions, no timed initial literals, no concurrency, and no preferences or soft goals.
  • No preferred operators. The FF heuristic returns an estimate but no preferred-operator set, so greedy search cannot use one.
  • Grounding is eager. The whole task is grounded before search begins, so an instance whose grounding does not fit in memory is out of reach regardless of how easy the search would have been.
  • A trivially unsolvable task is a crash, not a verdict. If a goal atom is neither reachable nor statically decided, translation stops with condition atom … has no SAS variable; it is neither reachable nor statically decided rather than reporting the task unsolvable. The result is correct in the sense that no plan exists, but it arrives as a panic and a non-zero exit status instead of a proof.
  • Most rejections are panics rather than errors. Only the S-expression reader and a handful of translation checks return a typed error; a construct outside the fragment usually aborts with a Rust panic message. It names what it choked on, but it is not a tidy diagnostic, and a construct that fails this way is easy to mistake for a bug in your PDDL when it is a limit of the translator.
