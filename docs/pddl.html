Supported PDDL

PlanForge reads a grounded fragment of numeric PDDL. This page lists what the translator accepts, construct by construct, and then the limits. The limits are not hidden at the bottom as a formality: reaching one is normally an explicit error naming the construct, not a silent reinterpretation of your task.

Input

Two positional arguments are a domain and a problem. One positional argument is a pre-translated SAS+ file.

planforge --search 'astar(lmcutnumeric())' domain.pddl problem.pddl
planforge --search 'astar(lmcutnumeric())' task.sas

On the PDDL route, translation and grounding happen in process: no SAS+ text is produced on the way to the planner's own search. When you want the text itself — to hand the task to another planner, or to attach it to a bug report — use the second binary, which stops after translation:

planforge-translator translate domain.pddl problem.pddl --output task.sas

Without --output it writes output.sas. Its one other option is --layer-strategy, which chooses how derived variables are spread over axiom layers: min, the default, puts as many as possible into one layer, and max gives every variable a layer of its own unless it sits in a cycle. A value that is neither is rejected while the command line is parsed:

$ planforge-translator translate --layer-strategy nope domain.pddl problem.pddl
error: invalid value 'nope' for '--layer-strategy <LAYER_STRATEGY>': unknown layer strategy "nope"; use `min` or `max`

Both routes reach the same task. Translating the delivery fixture from the quick start and searching the resulting SAS+ file reports the same 49 propositional and 12 numeric variables, expands the same 73 states and returns the same cost-22 plan as the single-call pipeline.

Domain sections

SectionHandling
:requirementsAccepted and ignored. The planner does not gate on the declared requirement flags; what it supports is what it parses, and an unsupported construct fails where it appears.
:typesRead, including type hierarchies. Untyped parameters default to object.
:constantsRead.
:predicatesRead.
:functionsRead. These are the numeric fluents.
:actionRead: :parameters, :precondition, :effect.
:derivedRead. Derived predicates become axioms, arranged into layers.
:global-constraintRead, as an axiom. A constraint required to hold in every state.
:axiomRejected, deliberately. PDDL 2.1's (:axiom :vars ... :context ... :implies ...) is a different block shape, not another spelling of :derived, and parsing it as one would silently mistake :vars for the head predicate. The error tells you to write (:derived (NAME ?x - t) CONDITION) instead.
anything elseSkipped, with a warning naming the section.

Conditions and goals

In preconditions, goals, axiom bodies and effect conditions:

  • and, or, not, imply.
  • forall and exists over typed parameter lists.
  • Numeric comparisons <, <=, =, >=, >, each over exactly two operands, and each also usable negated inside not. A comparison becomes a condition variable of its own, which is what lets the numeric CEGAR loop refine its operands.
  • Atoms and negated atoms.

= is read as a numeric comparison when either side looks numeric, so it serves both as equality between fluent expressions and as ordinary object equality.

Effects

  • Conjunctions of effects, and negated atoms as delete effects.
  • Conditional effects — when. Both propositional and numeric effects can be conditional.
  • Universal effects — forall.
  • Numeric assignment — all five PDDL operators: assign, increase, decrease, scale-up, scale-down. The target must be a primitive numeric expression, that is a function applied to arguments, rather than a compound expression.

Numeric expressions

Inside comparisons and assignments: numeric constants, function applications, the binary and n-ary operators +, -, *, /, and unary - as additive inverse. The fluent total-cost is recognised as the integer cost accumulator.

Problem sections

  • :objects, :init — including numeric initial assignments — and :goal.
  • :metric with minimize or maximize. See the limit below.

Limits

Abstractions require a conjunctive goal

Abstract operators are derived from task operators, and no task operator writes a derived variable — only the axioms do. A goal on a :derived predicate is therefore a goal an abstraction has nothing to reach for. Rather than let each abstraction family invent its own reading of such a goal, all of them refuse the task and name the variable and its axiom layer:

Error: Custom { kind: Other, error: "failed to build domain abstraction: CEGAR failed to build abstraction: abstractions support conjunctive goals only: goal fact Fact(var: 4, value: 0) names the derived variable \"var4\" (\"\") in axiom layer 1, which no operator writes" }

This covers a :derived predicate placed in the goal, and the goal-reachability predicate the translator introduces for a disjunctive, quantified or nested goal. Numeric comparisons are deliberately unaffected: a comparison variable is derived in the SAS sense too, but refining a comparison's operands is exactly what the numeric CEGAR loop does.

Nothing else is restricted this way. The same fixture that the domain abstraction refuses above solves normally under astar(lmcutnumeric()), at cost 5, because non-abstraction heuristics test the goal in a state the axiom evaluator has already closed.

Other limits, plainly

  • Plan metrics must name a single fluent. (:metric minimize (total-cost)) is used as written. A compound metric expression is not supported: it is replaced by total-cost, without an error. If your task minimises an arithmetic combination of fluents, PlanForge is not optimising what you wrote.
  • Pattern databases and Cartesian abstractions need a restricted task. Pass --restrict-task, or supply a task that is already restricted. Asking for these heuristics without it is an error that names the offending comparison axiom rather than a silent conversion.
  • Comparisons are binary. A comparison with more or fewer than two operands is rejected.
  • Assignment targets are primitive. The left-hand side of an assignment effect must be a function application, not an expression.
  • Sequential plans only. There are no durative actions, no timed initial literals, no concurrency, and no preferences or soft goals.
  • No preferred operators. The FF heuristic returns an estimate but no preferred-operator set, so greedy search cannot use one.
  • Grounding is eager. The whole task is grounded before search begins, so an instance whose grounding does not fit in memory is out of reach regardless of how easy the search would have been.

Benchmarks

The fixtures in the repository are small regression tasks, not a benchmark set, and no IPC data is redistributed here.
