PlanForge

PlanForge reads a planning task written in PDDL with numeric fluents, grounds it, and searches for a sequential plan. Under A* with an admissible heuristic the plan it returns is cost-optimal. It is one binary, and every configuration described on this site is reachable from that binary.

It is developed by MRlab, the Machine Reasoning Lab at Linköping University, and it began as a Rust port of Numeric Fast Downward, itself a fork of Fast Downward. That lineage is described on the credits page, together with the people and publications behind it and the licence terms it carries with it.

What it does

PlanForge has the same two-part structure as Fast Downward and its numeric extension: a translator that turns PDDL into a finite-domain SAS+ task, and a planner that searches that task under a choice of heuristics.

1. The translator: PDDL to SAS+

It reads a domain and problem pair, normalises away the constructs grounding cannot take directly, computes invariants to find finite-domain variables, and grounds the result. The fragment it handles correctly is, in terms of :requirements flags:

:strips :typing :negative-preconditions :action-costs :numeric-fluents :derived-predicates

plus two partial levels: :disjunctive-preconditions is compiled away in action preconditions but nowhere else, and :conditional-effects covers when but not forall. That is PDDL 2.1 level 1 — propositional and numeric, without time — plus PDDL 2.2 derived predicates.

It is not ADL, and the gap is not loud

Quantified preconditions and universal effects are parsed and then ignored. A forall precondition is treated as true, a forall effect is dropped, an exists precondition silently removes the action, and or outside an action precondition — in a goal, or in a :derived body — is treated as true. So a task using them does not get an error; it gets a wrong answer, which on the first and last of those can be an invalid plan.

Do not declare :adl and expect it to hold. The declared requirement list is never read, so no flag you write is checked against what is implemented. Supported PDDL lists every case, with the input that demonstrates it, and separates the constructs that fail loudly from the ones that fail quietly.

Translation and grounding happen in process, so the planner never writes SAS+ text on the way to its own search. A separate planforge-translator binary emits the text when the text itself is what you want; it writes format version 4, which is Fast Downward's SAS+ layout extended with numeric variables, comparison axioms and assignment axioms.

2. The planner: SAS+ to a plan

Three search engines — A*, greedy best-first search, and an A* variant that orders the open list with a cheap heuristic and confirms with an expensive one — over a heuristic library that includes blind search, numeric LM-cut, numeric pattern databases, CEGAR-built domain and Cartesian abstractions with maximising, canonical and saturated-cost-partitioning combinations, and an FF-style relaxed-plan heuristic. Most of the library is admissible and the table on the search page says which, because that is what decides whether a returned plan is optimal. LP-backed heuristics require an optional CPLEX build.

The plan is printed and written to sas_plan in the working directory, followed by a statistics block in the same shape Fast Downward prints; Output and exit codes covers what a script should test for. --max-time and --max-memory are enforced by the planner itself, so a task that runs out of either exits with a report instead of being killed from outside.

The current version is 0.1.0. The admissible paths (A* with blind, numeric LM-cut, pattern databases, and the canonical and saturated-cost-partitioning combinations of domain abstractions) are the ones the test suite pins instance by instance; preferred-operator support is not implemented.

Quick start

You need a stable Rust toolchain. The crates use edition 2024, so 1.85 or newer. Nothing else: no nightly features, no system libraries, no Python.

git clone https://github.com/mrlab-ai/PlanForge.git
cd PlanForge
cargo build --release --bin planforge

That produces target/release/planforge. The repository ships small PDDL fixtures under tests/assets/, so you can solve something immediately. This one is a numeric delivery task with two robots:

./target/release/planforge \
    --search 'astar(lmcutnumeric())' \
    tests/assets/numeric-pddl-files/delivery/domain.pddl \
    tests/assets/numeric-pddl-files/delivery/pfile1.pddl

It prints the plan, a statistics block and its search time, and leaves the plan in sas_plan, one grounded action per line in the usual parenthesised form:

(pick item2 rooma right1 bot1)
(pick item3 rooma left2 bot2)
(pick item1 rooma left1 bot1)
(move bot1 rooma roomc)
(drop item1 roomc left1 bot1)
(pick item4 rooma right2 bot2)
(move bot2 rooma roomb)
(drop item3 roomb left2 bot2)
(drop item4 roomb right2 bot2)
(drop item2 roomc right1 bot1)

Satisficing configurations

These are not comparable to the table above on cost, so they are not in it. Greedy best-first search does not order the open list on f = g + h and ff is not admissible; either one alone is enough to remove the optimality guarantee, and gbfs(ff()) has neither. The cost it returns is an upper bound on the optimum and nothing more:

gbfs(ff()) against the optimum on two fixtures. The "plan cost" column carries no optimality guarantee; the optimum beside it is from astar(lmcutnumeric()) on the same instance.
InstancePlan cost
(not guaranteed optimal)		Optimal costExpanded
delivery/pfile1.pddl222211

The two rows are the whole point. On delivery the returned cost happens to equal the optimum, after 11 expansions instead of 73 — which is why it is tempting to read a satisficing run as if it were an optimal one. On expedition the same configuration returns 54 against an optimum of 26, so the plan is more than twice as expensive as necessary; it also expands 2 786 states against A*'s 3 583, so it did not even buy much search. Neither number is a defect: an inadmissible heuristic under a greedy search is entitled to both results, and only the guarantee tells you which you are looking at.

Running a pre-translated task

When you want to translate once and search many times, translate to SAS+ first and hand the planner a single file:

./target/release/planforge-translator translate \
    tests/assets/numeric-pddl-files/delivery/domain.pddl \
    tests/assets/numeric-pddl-files/delivery/pfile1.pddl \
    --output delivery.sas

./target/release/planforge --search 'astar(lmcutnumeric())' delivery.sas

Both routes report the same 49 propositional and 12 numeric variables, expand the same 73 states and return the same cost-22 plan.
