Search configurations

One option, --search, selects the search engine and its heuristic. Its value is a nested call expression, and it defaults to astar(blind()). Always quote it: the parentheses are shell metacharacters.

The grammar

A configuration is a call. A call is a name, then a parenthesised and comma-separated argument list. An argument is either positional or key=value, and its value is a literal or another call. Whitespace after commas is ignored.

--search 'astar(blind())'
--search 'astar(lmcutnumeric())'
--search 'gbfs(ff())'
--search 'astar(domain_abstraction(), mpd=true)'
--search 'astar_fs(fast=lmcutnumeric(), slow=domain_abstraction())'
--search 'astar(canonical(domain(), cartesian()))'

A single redundant search(...) wrapper is accepted, so search(astar(blind())) parses as astar(blind()). An engine called with no argument gets blind. Anything the parser does not recognise is a hard error rather than a fallback: an unknown engine is rejected while the command line is being parsed, and an unknown heuristic is rejected before search starts, with the offending name quoted back at you.

$ planforge --search 'astar(nope())' domain.pddl problem.pddl
Error: Custom { kind: Other, error: "unknown heuristic `nope`" }

Engines

astar(<h>), optionally astar(<h>, mpd=true)
A*, ordering the open list on f = g + h. With an admissible heuristic the plan it returns is cost-optimal. mpd=true re-evaluates a state when it is popped rather than trusting the value it was inserted with, which pays off for heuristics that strengthen as construction continues.
gbfs(<h>)
Greedy best-first search, ordering on h alone. Often much faster than A* with the same heuristic, and with no optimality guarantee at all — the cost it returns is an upper bound on the optimum, whether or not the heuristic is admissible. This is the configuration to use with ff(), and the satisficing table shows it returning both an optimal and a two-times-optimal plan depending on the instance.
astar_fs(fast=<h>, slow=<h>)
A* with two heuristics. The cheap one orders the open list; the expensive one is evaluated lazily, when a state is about to be expanded, and the entry is reinserted with f = g + max(h_fast, h_slow). Both arguments are required and both must be named.

Because the key is a maximum, the search is optimal exactly when both heuristics are admissible — the maximum of two admissible estimates is admissible, but the maximum of an admissible and an inadmissible one is not. Nothing checks this: passing ff() in either slot is accepted and silently costs you the guarantee. Use the admissibility column below, or wrap the heuristic in check_admissible.

sgd(...)
Not a search engine. It synthesises a plan by gradient descent over a horizon-wide transcription of the task, with no open list and no state registry, and shares --search only to reuse the translation, resource-limit and plan-writing machinery. It requires the optional sgd build feature and reports no search statistics.

Heuristics

These are the names the heuristic factory accepts. Aliases are separated by a slash. Per-heuristic options are numerous and are documented where they are parsed, in planforge-search/src/heuristic_factory.rs and its abstraction_config module.

Always available

The admissibility column is the one that decides whether a plan is optimal: astar returns a cost-optimal plan with an admissible heuristic and merely a plan without one, and astar_fs needs both of its heuristics to be admissible. "Yes" here means admissible by construction, which the test suite pins instance by instance for the configurations it covers; if you want it verified for a state rather than asserted, wrap the heuristic in check_admissible.

blindyesZero on goal states and the task's minimum action cost elsewhere. The baseline, and the default.
lmcutnumericyesNumeric landmark-cut. Usable on its own or as the residual-cost component inside a cost partitioning.
ffnoRelaxed-plan heuristic with a monotonic numeric relaxation: each numeric variable carries a reachable (min, max) envelope through the relaxed planning graph, and a comparison becomes available once its envelope admits it. It can overestimate, so any plan cost obtained with it is an upper bound and not an optimum — under astar as much as under gbfs. It also refuses tasks with scale-up or scale-down effects, which a direction-agnostic monotonic relaxation cannot soundly bound, rather than returning an unsound estimate.

Error: Custom { kind: Other, error: "the requested LP-backed heuristic requires unrestricted CPLEX, which is not compiled into this build; rebuild with `--features cplex` and set CPLEX_ROOT" }

Abstraction sources

max, canonical and scp do not build abstractions themselves; they combine whatever they are given. What they are given is one or more sources, and a combinator with no source is an error:

$ planforge --search 'astar(max())' domain.pddl problem.pddl
Error: Custom { kind: Other, error: "`max` requires at least one domain(...), cartesian(...), cartesian_collection(...), icaps26_cartesian(...), or pdb(...) source" }
domain(...) / domain_abstractions(...)
Domain abstractions built by CEGAR.
cartesian(...) / cartesian_abstraction(...)
A single numeric Cartesian CEGAR abstraction.
cartesian_collection(...) / cartesian_abstraction_collection(...)
A collection of them, sized by max_states and max_collection_size.
icaps26_cartesian(...)
Cartesian abstractions under the published split-selection policies described on the credits page. It accepts pick=random|min_unwanted|max_unwanted and requires --restrict-task.
pdb(...) / numeric_pdb(...)
Numeric pattern databases.

Separating the two halves means the collection you build and the way you add it up vary independently. construction_max_time on the combinator is one shared budget covering both source generation and offline table construction.

planforge --search 'astar(canonical(domain()))' domain.pddl problem.pddl

planforge --restrict-task \
    --search 'astar(canonical(cartesian()))' domain.pddl problem.pddl

planforge --restrict-task \
    --search 'astar(canonical(cartesian_collection(max_states=1000,max_collection_size=100000),construction_max_time=900))' \
    domain.pddl problem.pddl

Pattern databases and Cartesian abstractions are defined over restricted tasks, so they ask for --restrict-task by name rather than guessing what you meant:

$ planforge --search 'astar(canonical(pdb()))' domain.pddl problem.pddl
Error: Custom { kind: Other, error: "task is not restricted: comparison axiom 0 has derived left operand 8; use `--restrict-task` or provide an already restricted task" }

Abstractions need a conjunctive goal

An abstract operator is derived from a task operator, and no task operator writes a derived variable — only the axioms do. A goal on a :derived predicate is therefore a goal an abstraction has nothing to reach for, so every abstraction family refuses such a task by name instead of inventing an interpretation of it. Numeric comparisons are deliberately unaffected; refining a comparison's operands is what the numeric CEGAR loop is for.

Non-abstraction configurations — blind, ff, lmcutnumeric — solve those tasks normally, because they test the goal in a state the axiom evaluator has already closed. See the limits section.

Checking a heuristic instead of trusting it

check_admissible(<h>) forwards every query to <h> and compares the answer against the true goal distance of the same state, which it computes by blind A* over the concrete task. An estimate above the true distance costs A* its optimality guarantee, so the wrapper reports it as an evaluation error rather than letting the search continue on a broken bound.

planforge --search 'astar(check_admissible(lmcutnumeric()))' \
    tests/assets/numeric-pddl-files/delivery/domain.pddl \
    tests/assets/numeric-pddl-files/delivery/pfile1.pddl

It is a development tool and it is expensive, because it solves the remaining task from scratch for every state it sees. On the delivery fixture used in the quick start, wrapping lmcutnumeric leaves the search identical — the same 73 expansions and the same cost-22 plan — and takes the search from about 0.04 seconds to about 49 seconds. Use it when you suspect a heuristic, not in an experiment.

Optional build features

Both optional features are off by default, and a default build does not compile their dependencies at all. CI has a job whose only purpose is to assert that, by inspecting the dependency graph rather than trusting the manifest.

cplex
The LP-backed heuristics, against the native IBM ILOG CPLEX 22.2 C API. Build with CPLEX_ROOT=/path/to/CPLEX_Studio/cplex cargo build --release --features cplex. CPLEX_ROOT must contain include/ilcplex/cplex.h and lib/x86-64_linux/static_pic/libcplex.a. The planner links the position-independent static library, uses one solver thread, and checks at heuristic start-up that the licence in force accepts and solves a 1001-column model, so a size-restricted licence such as the Community Edition is rejected up front rather than mid-experiment.
sgd
The gradient engine behind --search 'sgd(...)', and with it an autograd backend. Build with cargo build --release -p planforge --features sgd. Without the feature the engine is not silently absent — asking for it fails and says what to do: 
Error: Custom { kind: Other, error: "`sgd(...)` requires the `sgd` cargo feature; rebuild with `cargo build --release -p planforge --features sgd`" }

The rest of the command line

--max-time DURATION
Wall-clock budget, written as 45s, 30m or 1h.
--max-memory SIZE
Memory cap, written as 4096M or 8G. On Linux this is enforced against resident memory by a parent process, with a looser address-space limit behind it as a backstop, because the allocator reserves address space well ahead of the pages it commits. Heuristic construction and search give back a fixed memory reserve as the limit approaches, which buys enough room to exit with a report instead of being killed by an external Slurm or cgroup limit.
--restrict-task
Convert the task to its restricted representation; an already restricted task is left alone.
--compact-numeric-states
Store exact canonical numeric values behind checked 32-bit interned ids in the state registry, which shrinks states on tasks with many numeric variables.
--portfolio
Two sequential stages instead of one search: LM-cut under a tight budget, then canonical domain abstractions. Each stage is a child process, so the first stage's limits are actually enforced and the second starts clean. The per-stage budgets are --lmcut-time, --lmcut-memory, --canonical-construction-time, --canonical-memory and --canonical-time.
--log-level LEVEL
How much the planner prints. Informational output goes to standard output, warnings and errors to standard error.

Input is one positional argument for a SAS+ file, or two for a PDDL domain and problem. planforge --help prints the authoritative list.

Output and exit codes

A solved run prints the plan, then a statistics block in the same shape Fast Downward prints — plan length and cost, states expanded, reopened, evaluated and generated, dead ends, registered states and search time — and writes the plan to sas_plan in the working directory, one parenthesised grounded action per line. Informational output goes to standard output and warnings and errors to standard error, so redirecting one does not lose the other.

Exit status. The three named codes are the planner's own; a run killed by a signal exits with 128 plus the signal number, and a panic exits with Rust's 101.
CodeMeaning
0The planner ran to completion. This does not mean a plan was found — see below.
6The memory limit was reached.
7The time limit was reached.
101A panic: a construct outside the supported PDDL fragment, or a bug.

Exit 0 covers both "solved" and "searched exhaustively and found nothing"; the latter prints No solution found and writes no sas_plan. So a script must not read a zero status as success. Test for the plan file, or for Solution found! in the output.
