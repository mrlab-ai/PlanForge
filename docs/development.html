Development

PlanForge is a Cargo workspace of small crates on stable Rust. There is no build system beyond Cargo, no code generation step and no vendored C++. Everything below runs from a clone.

Building

cargo build --release            # both binaries
cargo build --release --bin planforge

The release profile uses link-time optimisation and a single codegen unit, so a full optimised build is around a minute of compiling rather than seconds. A second profile, experiment, keeps the optimiser but drops LTO for the cases where you are relinking after every one-line change.

Workspace layout

planforge
Both binaries — the planner and the translate-only staging tool — plus the command line, the reporting allocator, the resource limits, the portfolio and the plan output. This is the only crate that knows about processes and files.
planforge-searcher
The --search grammar: which engine, with which heuristics. Only the shape of a configuration lives here, which is why adding a heuristic never touches this crate.
planforge-search
The search engines, the heuristics and the abstractions. Adding a heuristic is a change to this crate alone: its own module, and one arm of heuristic_factory::build_heuristic_from_spec.
planforge-translate
The PDDL reader, grounder, invariant analysis and SAS+ writer.
planforge-sas
The task representation and the state registry that everything else is written against.
planforge-config-derive
The ApplyOptions derive macro. It is separate because a procedural macro has to be its own compilation unit, and it serves over a hundred --search options, deriving each configuration's positional-argument order from its field order.
planforge-cplex
A small checked wrapper over the native CPLEX C API and its sparse LP model. Optional; see the cplex feature.
planforge-sgd
The gradient plan-synthesis engine and its transcription. Optional; see the sgd feature.
planforge-py
Python bindings.
tests
The integration test suite, described below.

Tests

cargo test --workspace --exclude planforge-cplex

planforge-cplex is excluded because it links against a proprietary CPLEX installation that is not present on a normal machine or in CI.

The correctness gate is not a set of smoke tests. The tests crate pins the known optimal plan cost and plan length of every fixture under tests/assets/, and the tables of expected values are compared set-wise against the fixtures actually on disk. So a planner regression changes a plan cost and the suite fails, and adding a fixture without pinning its optimum also fails — you cannot quietly widen the corpus without stating what the right answer is. Alongside that, the suite covers translator output, preprocessor invariants, state-registry deduplication and heuristic admissibility.

Continuous integration

One workflow, .github/workflows/ci.yml, runs on every push to main and dev and on every pull request, with warnings promoted to errors. Six jobs:

JobWhat it enforces
rustfmtcargo fmt --all --check. Formatting is not a review topic.
clippyThe whole workspace, all targets, no warnings. The backlog was cleared to zero without adding suppressions to get there, so the job means "no new lints".
testThe suite above, in a debug build.
release testsThe optimised-only cases, which are the few instances whose search is minutes unoptimised and seconds optimised.
optional featuresCompiles and tests the sgd feature. Nothing else in CI would build it, so without this job the optional code would rot unnoticed.
default build excludes optional backendsInspects the dependency graph to prove a default build does not compile the autograd backend. The manifest is not accepted as evidence, because the dependency appears in Cargo.lock either way; only the build graph settles it.

The local verification gate

tools/gate.sh is the pre-commit counterpart. It is tiered because the checks answer different questions and the expensive ones are wasted on changes that cannot possibly alter behaviour:

tools/gate.sh fast [crate...]   # does the crate I touched still work?
tools/gate.sh semantic          # did plan costs or expansion counts move?
tools/gate.sh full              # the same, across the whole benchmark set
tools/gate.sh timing "astar(lmcutnumeric())"
tools/gate.sh all

Two things about it are worth knowing, because both were learned the hard way.

First, semantic and full compare plan costs and expansion counts against a saved baseline binary and deliberately ignore the clock. Costs and expansions are semantics: an optimisation level cannot change them, and identical counts are therefore a real gate where a timing comparison is noise.

Second, timing defaults to the default search configuration, astar(blind()) — which touches no heuristic code at all. If your change is in a heuristic, an abstraction, LM-cut or the numeric bounds, that tier exercises none of it and any difference it shows is machine drift. Pass a configuration that reaches your change. The script prints a warning when the configuration contains blind, and it interleaves the two binaries in ABBA order so that drift cancels rather than being reported as a speed-up.

Contributing

Bug reports and patches are welcome through the issue tracker and pull requests on GitHub. Two conventions worth knowing before you start:

  • A new heuristic is a local change. Add a module under planforge-search/src/evaluation/ and one arm to build_heuristic_from_spec. The --search parser does not need to learn the name, and neither does the command line.
  • Impossible states fail fast. The codebase prefers an assertion, a panic or a typed error over a conservative fallback. Validate external input and return a clear error; for a violated internal invariant, stop. Substituting a default for a missing value, or skipping data that does not parse, is the pattern most likely to be sent back in review.
